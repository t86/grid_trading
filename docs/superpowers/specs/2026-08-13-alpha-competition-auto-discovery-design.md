# Alpha 交易赛币种自动发现设计

日期：2026-08-13  
状态：已确认，待实现

## 1. 背景与故障事实

生产页面 `http://43.156.35.110/alpha/` 目前仍以 `ALPHA_SYMBOLS` 作为展示名单。后端虽有一份未提交的自动发现尝试，但新公告 DOS 在解析时因标题符号与正文轮次名称不一致而失败，异常又被逐币种跳过，因此页面没有提示，也没有加入 DOS。

用户要求公告发布后自动加入新交易赛币种，比赛过期后自动剔除，全程不依赖人工修改币种配置或重启服务。

## 2. 已确认行为

- Binance 发布符合条件的 Alpha 交易赛公告后，页面立即显示该币种。
- 公告已发布但首轮尚未开始时，状态显示为 `upcoming`（未开始）。
- 当前时间进入任一公告周期后，状态自动切换为 `active`（进行中）。
- 当前时间达到公告最后一个周期的结束时刻后，币种自动从页面名单剔除。
- 时间区间统一使用 UTC 左闭右开语义 `[start, end)`。
- 正常运行不再依赖 `ALPHA_SYMBOLS` 人工维护；该配置只作为旧告警流程的兼容输入，不决定交易赛页面名单。

## 3. 数据源与身份规则

### 3.1 公告发现

使用 Binance 官方 CMS `catalogId=93` 公告列表，初次启动回溯最近 60 天，稳定运行后每 5 分钟刷新。标题必须匹配 `Binance Alpha Trading Competition:`，并从标题括号中提取交易币种符号。

每篇公告以 `article code` 为唯一键。币种符号不是公告主键，因为同一币种未来可能发布多轮不同公告。

### 3.2 标题与正文身份

标题括号中的符号是页面和 Alpha 交易对使用的规范符号。正文轮次标签可以使用币种全名、项目名或规范符号；例如 DOS 公告标题为 `DAPPOS (DOS)`，正文可能写 `DAPPOS Trading Competition Promotion Period`。

解析器不得要求正文轮次标签与标题符号逐字相等。它只要求同一篇公告内所有显式轮次标签一致，并以标题符号作为最终 `symbol`。这样既兼容 DOS，又不会把另一币种的轮次误并入当前公告。

## 4. 服务端结构与数据流

### 4.1 `BinanceCompetitionRuleProvider`

- 分页读取最近 60 天公告并返回候选公告元数据；
- 从标题提取规范符号；
- 拉取公告详情并解析轮次、每日倍速和获奖人数；
- 对同一公告的轮次标签一致性、时间连续性、倍速和人数做严格验证。

### 4.2 `CompetitionDiscoveryCache`

持久化到现有专用缓存目录，记录：

- 最近一次完整成功扫描时间；
- 每个 article code 的标题、规范符号、发布日期、解析后的规则和最后验证时间；
- 最近一次成功得出的 `upcoming + active` 页面集合。

写入采用临时文件加同目录原子替换，并沿用现有缓存目录权限。

### 4.3 `CompetitionDiscoveryService`

每次 API 请求读取内存快照；快照超过 5 分钟时由单个线程刷新，其他并发请求继续使用旧快照，避免重复抓取 CMS。

成功刷新时：

1. 合并新公告和缓存中的尚未结束公告；
2. 对新公告或已更新公告解析详情；
3. 根据当前时间保留 `upcoming` 与 `active`；
4. 剔除 `ended`；
5. 原子保存并发布新快照。

`/api/competition` 与 `/api/snapshot` 使用同一动态符号快照，避免上下两张表币种不一致。

## 5. 故障与降级

- 公告列表请求失败：继续使用最近一次完整成功快照，并标记 `discoveryStale=true`，不得清空名单。
- 单篇新公告解析失败：返回该公告的受控错误，保留其他币种；如果该 article code 有旧规则，则继续使用旧规则并标记陈旧。
- 已缓存公告详情刷新失败：保留旧规则直到其已知最后结束时间；不得因网络失败提前剔除。
- 完整扫描成功且当前时间已超过某公告最后结束时间：正常剔除，不再依赖旧环境变量兜底。
- 首次启动无缓存且 Binance 不可用：API 返回明确的发现错误和空列表，不把人工名单冒充自动发现结果。
- 不再静默吞掉 DOS 这类解析错误；错误需进入 API `errors` 和服务日志，但不能中断其他币种。

## 6. API 与页面

`GET /api/competition` 保留现有行字段，并新增顶层发现状态：

```json
{
  "generatedAtUtc": "2026-08-13T02:00:00+00:00",
  "discoveredAtUtc": "2026-08-13T01:58:00+00:00",
  "discoveryStale": false,
  "rows": [],
  "errors": []
}
```

`upcoming` 行展示公告链接、获奖人数、首轮开始时间和开始倒计时；尚未开始时不计算成交量或门槛。`active` 行按现有规则展示倍速、加权总量与门槛。`ended` 行不返回页面。

页面继续每 30 秒刷新行情和指标；公告源实际抓取由服务端 5 分钟 TTL 控制。发现数据陈旧时，页面显示醒目的“公告发现数据已过期”提示，同时保留最后成功内容。

## 7. 部署边界

- 本地 `main` 是唯一正式源码；生产目录中的未提交临时代码不得继续作为唯一实现。
- 先保全并审计生产 diff，只移植本需求所需的自动发现改动；不得覆盖其中与实际榜单门槛有关的其他临时工作。
- 变更提交并推送到 `origin/main` 后，生产服务器只通过 Git 拉取更新，不复制或粘贴代码。
- 部署后服务工作树必须干净，systemd 服务运行 commit 必须与已推送的 `main` 一致。

## 8. 测试与验收

测试遵循先失败后实现，至少覆盖：

1. 真实 DOS 公告：标题符号为 DOS、正文轮次标签为 DAPPOS，规则解析成功；
2. 公告发布且未开始时立即返回 `upcoming`；
3. 到开始时刻自动切为 `active`；
4. 到最后结束时刻自动从结果中剔除；
5. 新公告在无需修改 `ALPHA_SYMBOLS`、无需重启的情况下进入两个 API；
6. 扫描失败保留最近一次成功名单并标记陈旧；
7. 单篇坏公告不影响其他健康币种，且错误可见；
8. 多次并发刷新不会重复扫描 CMS；
9. 缓存重启恢复、原子写入和损坏缓存恢复；
10. 桌面与移动端均能显示 upcoming、active 和陈旧提示且无横向溢出。

生产验收以 Binance 当前公告为准：DOS 应立即出现在页面；POWER、QUID、GRVT、CAP 等按实际时间显示，PRL 等已结束公告自动剔除。等待跨越时间边界不是必须条件，状态切换使用冻结时钟自动测试证明。
